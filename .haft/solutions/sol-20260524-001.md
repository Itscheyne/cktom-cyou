# Solutions for: Persistent storage backend for Talos Linux / K8s homelab

Problem: prob-20260524-001

## Variants (5)

### V1. Longhorn

CNCF-graduated distributed block storage. Runs entirely as Kubernetes workloads — no host daemons. Requires Talos system extension for iscsi-tools and util-linux-tools. Web UI included.

**Strengths:**
- Pure K8s deployment — no out-of-cluster components
- CNCF graduated — well-maintained, large homelab community
- Built-in snapshot/backup to S3-compatible targets
- Web UI for volume management and health monitoring
- RWO + RWX (via NFS on top of block volumes)

**Novelty:** Only option that is fully in-cluster with no external dependencies and has a management UI

**Weakest link:** Requires two Talos system extensions (iscsi-tools, util-linux-tools) — must be baked into node image via Talos Image Factory or local build. Any node rebuild must re-include extensions or volumes go offline.

**Risks:**
- Extension image rebuild required on every Talos upgrade
- High CPU/memory overhead per node (replicated I/O path)
- RWX support is NFS-backed — adds latency vs native block

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Backup-to-S3 feature enables migration path to external storage later. Snapshot CRDs align with Velero.

**Diversity role:** In-cluster replicated block storage, Talos extension required

**Rollback:** Drain workloads off Longhorn PVCs, delete Helm release and CRDs. Data on raw disks remains but is not accessible without Longhorn.

### V2. democratic-csi + NFS/iSCSI (TrueNAS/Proxmox NFS)

democratic-csi is a CSI driver that delegates actual storage to an external NAS (TrueNAS Scale, TrueNAS Core, or Proxmox-hosted NFS share). The K8s cluster provisions PVCs; the NAS holds all data. No in-cluster replication — durability comes from the NAS RAID/ZFS.

**Strengths:**
- Zero Talos extensions needed — pure userspace CSI driver
- Durability is external to cluster — node loss never risks data
- ZFS on TrueNAS gives snapshots, compression, checksumming for free
- Supports RWO (iSCSI), RWX (NFS), ROX natively
- democratic-csi supports many backends — not locked to one NAS product

**Novelty:** Only option where data durability is fully external to K8s — survives complete cluster destruction

**Weakest link:** Entire cluster's persistent storage depends on a single external NAS. NAS becomes a hard single point of failure and must be separately maintained, backed up, and monitored.

**Risks:**
- NAS downtime = all PVCs unavailable cluster-wide
- iSCSI path needs network reliability (jumbo frames, dedicated VLAN recommended)
- Adds another system (TrueNAS VM or dedicated box) to maintain

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** NAS-backed storage decouples data from cluster entirely — natural foundation for multi-cluster or cluster-rebuild scenarios.

**Diversity role:** External NAS delegation, no in-cluster replication, no Talos extensions

**Rollback:** Delete CSI driver. PVC data remains on NAS filesystem — accessible directly via NFS/iSCSI mounts outside K8s.

### V3. Rook/Ceph

Rook is a CNCF-graduated K8s operator that deploys and manages a full Ceph cluster inside Kubernetes. Provides block (RBD), filesystem (CephFS), and object (RGW) storage. Requires Talos system extension for rbd kernel module.

**Strengths:**
- Production-grade distributed storage — survives multiple simultaneous node failures with proper replication factor
- Block + filesystem + object from one system
- CNCF graduated, battle-tested at scale
- CephFS provides native RWX without NFS overhead

**Novelty:** Only option providing native object storage (S3-compatible RGW) alongside block and filesystem from one system

**Weakest link:** Operational complexity is the highest of any option. Ceph requires minimum 3 dedicated OSD nodes (or 3 nodes with dedicated disks), significant RAM per OSD (2-4GB+), and deep Ceph knowledge to debug. Homelab misconfigurations commonly cause split-brain or data loss.

**Risks:**
- Memory hungry — each OSD daemon needs 2-4GB RAM minimum
- Debugging Ceph failures requires Ceph expertise, not just K8s knowledge
- Rook requires Talos rbd extension — same image rebuild burden as Longhorn
- Overkill for single homelab operator — ops cost exceeds benefit

**Diversity role:** Full distributed storage stack, highest complexity and capability ceiling

**Rollback:** Extremely difficult. Rook/Ceph data is distributed across all nodes in Ceph format — not readable without Ceph. Full removal requires wiping all OSD disks.

### V4. Proxmox CSI Plugin (proxmox-csi-plugin)

CSI driver that provisions Proxmox storage volumes (via Proxmox API) and attaches them to VMs as virtual disks. PVCs map to actual Proxmox storage (LVM, ZFS, Ceph, NFS — whatever Proxmox is configured with). No in-cluster storage component at all.

**Strengths:**
- Zero in-cluster storage overhead — no storage pods consuming resources
- No Talos extensions required — volumes attach as virtual block devices
- Durability inherits from Proxmox storage backend (e.g. Proxmox Ceph or ZFS pool)
- Natural fit for Proxmox-hosted Talos — leverages existing infrastructure

**Novelty:** Only option with zero K8s-side storage components — all persistence is Proxmox-native virtual disks

**Weakest link:** Proxmox API availability gates all storage operations. Volume attach/detach goes through Proxmox — slow (seconds, not milliseconds) and fails if Proxmox API is unreachable. Not suitable for high-churn PVC workloads.

**Risks:**
- VM must be on same Proxmox node as the volume unless shared storage configured in Proxmox
- Volume migration on pod reschedule requires live migration or volume detach/reattach — adds scheduling latency
- Vendor-tied to Proxmox — unusable if cluster migrates away from Proxmox

**Diversity role:** Hypervisor-delegated storage, no in-cluster components, Proxmox-coupled

**Rollback:** Delete CSI driver. Proxmox volumes remain as detached VM disks — data accessible by manually attaching to any VM.

### V5. local-path-provisioner (Rancher)

Simplest possible option. Provisions PVCs as directories on the local node filesystem. No replication, no network storage. Data lives on whichever node the pod lands on.

**Strengths:**
- Trivially simple — one Helm chart, no extensions, no external deps
- Highest I/O performance — no network overhead
- Zero ops burden
- Good for dev/test workloads and non-critical data (caches, ephemeral queues)

**Novelty:** Only option with zero network I/O — pure local disk performance, zero complexity

**Weakest link:** No durability — pod rescheduled to different node cannot access its data. Effectively non-HA for stateful workloads.

**Risks:**
- Node failure = data loss for all PVCs on that node
- No snapshots, no backup integration
- Ties pod scheduling to specific nodes (node affinity required)

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Useful as bootstrap layer while choosing and deploying a real storage solution. Can coexist with any other option via separate StorageClasses.

**Diversity role:** Local node storage, no durability, max simplicity

**Rollback:** Delete Helm release. Data remains in local directories on each node filesystem.

## Non-Dominated Set

**Computed Pareto front:** Longhorn, democratic-csi + NFS/iSCSI (TrueNAS/Proxmox NFS), Rook/Ceph, Proxmox CSI Plugin (proxmox-csi-plugin), local-path-provisioner (Rancher)

## Dominated Variant Elimination

- Rook/Ceph — dominated by Longhorn, democratic-csi + NFS/iSCSI (TrueNAS/Proxmox NFS). Higher ops complexity than all alternatives with no compensating win for a homelab. V1 gives replicated block at lower ops cost; V2 gives external durability with zero extensions. Rook/Ceph only wins on S3 object storage — not a stated requirement.
- local-path-provisioner (Rancher) — dominated by Proxmox CSI Plugin (proxmox-csi-plugin). Same ops_complexity (low), same Talos compatibility (native), same RWO-only support as V4 — but V5 has zero durability vs V4 external. No target dimension where V5 beats V4.

## Pareto Front Trade-Offs

- Longhorn — Best maturity + in-cluster replication. Sacrifices: needs Talos extensions (upgrade friction), medium ops complexity, 3x storage overhead.
- democratic-csi + NFS/iSCSI (TrueNAS/Proxmox NFS) — Best durability (external, survives cluster destruction) + no extensions. Sacrifices: NAS is hard SPOF, requires maintaining separate system, democratic-csi less mature.
- Rook/Ceph — Eliminated — dominated by V1 and V2. Included in tradeoffs for completeness: highest capability ceiling (S3, CephFS RWX) but highest ops cost with no homelab-relevant advantage over V1/V2.
- Proxmox CSI Plugin (proxmox-csi-plugin) — Lowest ops complexity + no extensions + external durability. Sacrifices: RWO only, Proxmox vendor lock-in, slower volume attach, newer project maturity.
- local-path-provisioner (Rancher) — Eliminated — dominated by V4. Included for completeness: simplest possible option but zero durability makes it unsuitable as primary storage.

**Selection policy:** Minimize ops burden for solo homelab operator. Prefer data durability over performance. Prefer no Talos extensions if ops complexity equal. Break ties on maturity.

**Recommendation (advisory):** Longhorn

**Recommendation rationale:** V1 (Longhorn) best balances ops complexity and maturity for solo operator. Extension rebuild is one-time per Talos upgrade, well-documented in homelab community. In-cluster replication means no external dependency. RWX available when needed. V2 preferred if TrueNAS already exists; V4 if workloads are RWO-only and Proxmox coupling is acceptable.
