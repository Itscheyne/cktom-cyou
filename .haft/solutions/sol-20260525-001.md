# Solutions for: Secure GitOps pipeline: agent-assisted IaC dev → PR review → automated prod apply

Problem: prob-20260525-001

## Variants (4)

### V1. Self-hosted GHA runner on Proxmox + GitHub Secrets

A self-hosted GitHub Actions runner VM lives inside the Proxmox network. It has native API access to all Proxmox nodes. Prod secrets stored in GitHub repository secrets, injected as env vars at job time. Agents on dev workstation use a separate read-only Proxmox token for tofu plan.

**Strengths:**
- Runner on same L2/L3 as Proxmox API — no VPN, no firewall punching, native reachability
- GitHub Secrets are encrypted at rest, never logged, never in git — low credential exposure for prod creds
- Self-hosted runner keeps all Tofu state and provider cache local — fast plan/apply cycles
- Audit trail: every apply tied to a GHA run ID, commit SHA, and PR merge event

**Novelty:** Only variant with native Proxmox network access — no VPN layer required

**Weakest link:** Runner VM is itself a privileged host inside the production network. If it is compromised (via a malicious GHA workflow, supply chain attack on a workflow action, or misconfigured repo permissions), attacker has direct Proxmox API access and injected secrets. Runner security is the entire trust boundary.

**Risks:**
- Repo must be private or runner scoped to org — public repo + self-hosted runner is a known RCE vector
- Runner VM requires maintenance (OS updates, GHA runner agent upgrades)
- GitHub Secrets rotation requires manual update in GitHub UI — no auto-rotation

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Runner VM can later run other automation (Ansible, kubectl, talosctl). GitHub Secrets can be replaced with OIDC/Vault without changing runner architecture.

**Diversity role:** Lowest ops path for network reachability, medium credential risk

**Rollback:** Remove GHA workflows, revoke runner registration token, delete runner VM. Revert to manual tofu apply from workstation.

### V2. Cloud GHA runner + Netbird VPN tunnel for Proxmox access

Standard GitHub-hosted runners (ubuntu-latest) run the pipeline. A Netbird peer is pre-joined to the homelab mesh; the runner installs the Netbird client ephemerally at job start using a one-time setup key, joins the mesh, then runs tofu plan/apply against Proxmox via VPN. Prod secrets in GitHub Secrets.

**Strengths:**
- No infra to maintain for the runner — GitHub manages it, always up to date
- Netbird setup key is ephemeral — runner joins mesh for the duration of the job only, then key is invalidated
- Isolates runner from prod network by default — VPN join is an explicit, auditable step
- GitHub-hosted runners have no persistent state — harder to pivot from a compromised run

**Novelty:** Only variant with zero self-hosted runner infra — all CI managed by GitHub

**Weakest link:** Netbird setup key stored in GitHub Secrets is the trust anchor. Any workflow that can read secrets can join the production VPN mesh with full peer access. Key rotation requires manual invalidation and re-creation of the secret — there is no automatic expiry enforcement at the network layer.

**Risks:**
- Netbird client install + join adds 30-60s to every pipeline run
- If Netbird management plane (cloud or self-hosted) is unavailable, pipeline is blocked
- Setup key scope must be tightly restricted — wrong ACL = runner gets broader mesh access than intended

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Netbird mesh already used for Talos cluster. Ephemeral runner pattern generalises to any cloud CI system (GitLab CI, Buildkite). OIDC can replace GitHub Secrets for the Netbird key later.

**Diversity role:** Zero runner maintenance, VPN-mediated network access, ephemeral runner identity

**Rollback:** Remove GHA workflows, invalidate Netbird setup key. No runner VM to decommission. Revert to manual apply.

### V3. Self-hosted GHA runner + HashiCorp Vault for dynamic secrets

Self-hosted runner inside Proxmox network (same as V1) but secrets are never stored in GitHub. Instead, Vault runs as a VM in the homelab. The GHA workflow authenticates to Vault via JWT (GitHub OIDC), receives short-lived dynamic Proxmox credentials, runs tofu plan/apply, and credentials expire automatically. Agents use Vault AppRole for read-only tokens.

**Strengths:**
- Dynamic secrets: Proxmox credentials issued per-job with TTL, automatically revoked — eliminates static secret rotation burden
- GitHub OIDC → Vault JWT auth: no long-lived secrets stored in GitHub at all
- Vault audit log gives fine-grained record of every secret issuance, by which workflow, at what time
- Agents get read-only Vault AppRole — single place to manage all credential tiers

**Novelty:** Only variant with dynamic, auto-expiring credentials and full audit log of secret issuance

**Weakest link:** Vault is a new production dependency. If Vault is unavailable (VM down, storage corrupt, seal lost), the entire pipeline is blocked — no credentials, no apply. Unsealing Vault after a reboot requires manual intervention unless auto-unseal is configured (which adds another dependency: cloud KMS or another HSM).

**Risks:**
- Vault HA requires at least 3 nodes for Raft — single-node Vault is a SPOF
- Auto-unseal requires external KMS (AWS KMS, cloud provider) — adds cloud dependency to an otherwise self-hosted stack
- Vault itself requires IaC, backup, and upgrade management — significant ops overhead for a solo homelab

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Vault enables secrets for all future homelab services (K8s, databases, apps) not just Tofu. Foundational for zero-trust posture.

**Diversity role:** Highest security ceiling, highest ops complexity, Vault as central trust anchor

**Rollback:** Fall back to GitHub Secrets (V1/V2). Vault data can be archived. Runner VM persists and can be repurposed.

### V4. Self-hosted Forgejo/Gitea + Forgejo Actions runner (fully self-hosted GitOps)

Replace GitHub entirely with a self-hosted Forgejo instance (lightweight Gitea fork) running inside the homelab. Forgejo Actions is API-compatible with GitHub Actions. Runner lives on Proxmox network natively. Secrets stored in Forgejo's encrypted secret store. No external dependency on GitHub for the pipeline.

**Strengths:**
- Entire GitOps stack runs inside the homelab — no GitHub dependency for CI/CD
- Runner natively on Proxmox network — same reachability advantage as V1 without GitHub as intermediary
- Forgejo secret store is under operator control — rotation, access policy, audit all local
- Forgejo Actions uses the same workflow YAML syntax as GHA — migration path to/from GitHub is low friction

**Novelty:** Only fully air-gapped variant — zero GitHub dependency in the pipeline

**Weakest link:** Forgejo instance itself must be highly available and backed up. If Forgejo is down, the entire pipeline (git hosting + CI) is unavailable. A homelab Forgejo with no HA is a SPOF for all code and all automation simultaneously — losing it means losing both the repo and the pipeline in one failure.

**Risks:**
- Requires maintaining Forgejo VM (upgrades, storage, TLS certs, backups)
- No GitHub PR review UX, ecosystem integrations (Dependabot, CodeQL, third-party apps) are lost
- Significantly higher bootstrapping effort — must self-host git before any IaC can be stored

**Diversity role:** Maximum sovereignty, maximum maintenance burden, no external SaaS

**Rollback:** Mirror repo back to GitHub. GHA workflows reusable as-is. Decommission Forgejo VM.

## Dominated Variant Elimination

- Self-hosted Forgejo/Gitea + Forgejo Actions runner (fully self-hosted GitOps) — dominated by Self-hosted GHA runner on Proxmox + GitHub Secrets, Cloud GHA runner + Netbird VPN tunnel for Proxmox access. V4 matches V1 on credential_exposure_risk (both medium) but ops_complexity is higher (high vs medium) with no compensating win. V2 beats V4 on ops_complexity (low vs high). V4's only differentiator is GitHub independence — not a stated requirement. Forgejo SPOF (git + CI in one VM) and bootstrapping cost make it strictly worse for a solo operator.

## Pareto Front Trade-Offs

- Self-hosted GHA runner on Proxmox + GitHub Secrets — Best balance of ops_complexity and native network reachability. Sacrifices: runner VM to maintain, static GitHub Secrets (medium credential risk). Wins: native Proxmox access, no VPN overhead, simplest mental model.
- Cloud GHA runner + Netbird VPN tunnel for Proxmox access — Lowest ops_complexity — no runner VM. Sacrifices: Netbird VPN overhead per job (30-60s), tunneled vs native reachability, setup key is trust anchor. Wins: zero runner maintenance, ephemeral runner identity, Netbird already in stack.
- Self-hosted GHA runner + HashiCorp Vault for dynamic secrets — Best credential_exposure_risk and secret_rotation_burden. Sacrifices: highest ops_complexity (Vault VM, unseal, HA). Wins: dynamic creds, OIDC auth, fullest audit trail. Stepping stone to full zero-trust.
- Self-hosted Forgejo/Gitea + Forgejo Actions runner (fully self-hosted GitOps) — Eliminated — dominated by V1 and V2. Included for completeness: only variant with full GitHub independence, but Forgejo SPOF and ops overhead outweigh the sovereignty benefit for a solo homelab operator.

**Selection policy:** Minimize ops complexity for solo operator. Treat credential_exposure_risk and proxmox_network_reachability as hard constraints (must not be high-risk or blocked). Break ties on agent_readonly_feedback_speed.

**Recommendation (advisory):** Cloud GHA runner + Netbird VPN tunnel for Proxmox access

**Recommendation rationale:** V2 wins on ops_complexity (no runner VM), uses Netbird already in the stack, and matches V1 on auditability and agent feedback speed. Netbird setup key risk is manageable: restrict key to dedicated GHA peer tag, ACL to Proxmox API ports only. V1 is fallback if VPN latency is unacceptable. V3 deferred until Vault HA is feasible.
