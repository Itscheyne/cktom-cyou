# Secure GitOps pipeline: agent-assisted IaC dev → PR review → automated prod apply

## Signal

No CI/CD pipeline exists. Tofu apply runs manually from dev workstation with full prod credentials. Agents developing IaC have no read-only access to live infra for planning. No gate between code review and production apply.

## Constraints

- Agents on dev workstation get read-only infra access only — never write credentials
- Production apply (tofu apply) runs ONLY via GitHub Actions on main branch merge — never from dev workstation
- Secrets (Proxmox credentials, Talos keys) must never appear in git history or Actions logs
- GitHub Actions runner must have network access to Proxmox API endpoints
- tofu plan must run before tofu apply in the same pipeline — no apply without a passing plan

## Optimization Targets

- Minimize blast radius of credential exposure — least-privilege at every stage
- Eliminate manual tofu apply from prod — all prod changes via PR merge only
- Minimize friction in agent-assisted dev loop — read-only plan feedback fast

## Observation Indicators

- Pipeline execution time (plan + apply)
- Number of manual interventions required per deploy
- Drift between main branch state and live infra state

## Acceptance

Agent on dev workstation can run tofu plan against live infra read-only. PR merge to main triggers GHA runner that runs tofu plan then tofu apply with prod secrets injected. No prod credentials stored on dev workstation or in git.

## Blast Radius

All production infrastructure (Proxmox nodes, Talos cluster, networking). GitHub repo secrets. Dev workstation credential store.

## Reversibility

medium

|-----------|------|-------|------|----------|-------------|
| credential_exposure_risk | target | ordinal | level | lower_better | low (creds never leave secrets backend, injected ephemerally) / medium (creds stored in GHA secrets, rotated manually) / high (creds on disk or in env vars accessible to agents) |
| proxmox_network_reachability | target | ordinal | level | higher_better | native (runner on same network as Proxmox API) / tunneled (VPN/Netbird required) / blocked (no path without infra changes) |
| ops_complexity | target | ordinal | level | lower_better | low (managed GHA runner + GitHub Secrets, no extra infra) / medium (self-hosted runner or secrets backend to maintain) / high (multiple extra systems: Vault + runner + VPN) |
| agent_readonly_feedback_speed | target | ordinal | level | higher_better | fast (tofu plan runs locally against live infra in <60s) / medium (plan runs in CI only, feedback after push) / slow (no live plan, dry-run only) |
| secret_rotation_burden | target | ordinal | level | lower_better | low (secrets rotated in one place, auto-propagated) / medium (manual update in 1-2 places) / high (manual update in 3+ places or no rotation path) |
| auditability | target | ordinal | level | higher_better | high (every apply tied to PR + commit + GHA run log) / medium (apply logged but not linked to PR) / low (manual apply, no audit trail) |

**Parity rules:** All variants evaluated assuming: 3-node Proxmox homelab, GitHub-hosted repo, single operator. No variant gets dedicated secret management infra unless that is its native model. Read-only agent access evaluated on same dev workstation in all cases.
