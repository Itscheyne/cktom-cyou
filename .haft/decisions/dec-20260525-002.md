# Cloud GHA runner + Netbird VPN tunnel for Proxmox access

## 1. Problem Frame

**Signal:** No CI/CD pipeline exists. Tofu apply runs manually from dev workstation with full prod credentials. Agents developing IaC have no read-only access to live infra for planning. No gate between code review and production apply.

**Constraints:**
- Agents on dev workstation get read-only infra access only — never write credentials
- Production apply (tofu apply) runs ONLY via GitHub Actions on main branch merge — never from dev workstation
- Secrets (Proxmox credentials, Talos keys) must never appear in git history or Actions logs
- GitHub Actions runner must have network access to Proxmox API endpoints
- tofu plan must run before tofu apply in the same pipeline — no apply without a passing plan

**Acceptance:** Agent on dev workstation can run tofu plan against live infra read-only. PR merge to main triggers GHA runner that runs tofu plan then tofu apply with prod secrets injected. No prod credentials stored on dev workstation or in git.

## 2. Decision

**Selected:** Cloud GHA runner + Netbird VPN tunnel for Proxmox access

**Selection policy:** Minimize ops complexity for solo operator. Credential_exposure_risk and proxmox_network_reachability treated as hard constraints. Break ties on agent_readonly_feedback_speed.

**Why selected:** Lowest ops complexity — no runner VM to maintain. Netbird already in the stack (Talos nodes on the mesh), so no new system introduced. Matches V1 on auditability and agent feedback speed. Credential risk equal to V1 and manageable with tight Netbird ACL scoping to Proxmox API ports only.


**Invariants:**
- tofu plan must succeed before tofu apply runs in every pipeline execution
- Prod apply runs only on merge to main — never on PR branches
- Netbird setup key ACL must restrict GHA peer to Proxmox API ports only (8006/tcp)
- Proxmox read-only token used by agents on dev workstation — never the prod token
- Prod secrets never written to disk or logs — injected as env vars only

**Pre-conditions:**
- [ ] Netbird management plane reachable (self-hosted or cloud)
- [ ] Dedicated Netbird setup key created with restricted ACL (GHA peer tag, Proxmox API ports only)
- [ ] Read-only Proxmox API token created for agent dev workstation use
- [ ] GitHub repository is private (required for self-hosted runner security model — applies here too as Netbird key is in repo secrets)
- [ ] GitHub Actions enabled on repo with branch protection on main (require PR + review before merge)

**Post-conditions:**
- [ ] PR merge to main triggers GHA workflow automatically
- [ ] Workflow installs Netbird, joins mesh, runs tofu plan, runs tofu apply, exits mesh
- [ ] Every apply is traceable to a PR number, commit SHA, and GHA run ID
- [ ] Dev workstation can run tofu plan with read-only token without triggering any prod change
- [ ] Netbird peer for GHA runner appears and disappears per job — no persistent peer

**Admissibility:**
- NOT: Must not store Proxmox write credentials on dev workstation
- NOT: Must not run tofu apply from dev workstation or PR branches
- NOT: Must not use a Netbird setup key with unrestricted mesh access
- NOT: Must not disable branch protection on main

## 3. Rationale

**Counterargument:** V1 (self-hosted runner) avoids Netbird management plane as a pipeline dependency and eliminates VPN join latency. If Netbird cloud is used (not self-hosted), it introduces an external SaaS dependency into the pipeline critical path.

**Selected variant weakest link:** Netbird setup key stored in GitHub Secrets is the trust anchor. Any workflow that can read secrets can join the production VPN mesh. Netbird management plane availability gates every pipeline run.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Cloud GHA runner + Netbird VPN tunnel for Proxmox access | **Selected** | Lowest ops complexity — no runner VM to maintain. Netbi... |
| Self-hosted GHA runner + GitHub Secrets | Rejected | Requires maintaining a runner VM inside the prod network. Higher ops burden than V2 with no security advantage — both use static GitHub Secrets. |
| Self-hosted GHA runner + Vault | Rejected | Best credential posture but highest ops complexity. Vault SPOF blocks all pipelines if down. Deferred until Vault HA is feasible. |
| Forgejo fully self-hosted | Rejected | Dominated by V1 and V2. Forgejo SPOF combines git hosting and CI in one VM. No compensating benefit for a solo operator. |

**Evidence requirements:**
- Verify Netbird setup key can be scoped to peer tags and port-level ACLs in current Netbird version
- Test ephemeral Netbird join/leave in a GHA workflow (ubuntu-latest)
- Confirm tofu plan succeeds against Proxmox API via Netbird tunnel from GHA runner
- Verify Proxmox read-only token prevents any write operations (tofu apply fails with read-only token)

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Pipeline completes plan+apply within acceptable time | GHA run wall-clock time including Netbird join | Under 10 minutes for typical tofu apply |
| Netbird ACL prevents lateral movement | GHA runner peer cannot reach any host except Proxmox API endpoints on port 8006 | All other traffic blocked, verified by ACL audit in Netbird admin |

## 4. Consequences

**Rollback plan:**
Triggers:
- Netbird management plane reliability drops below acceptable threshold
- VPN join latency exceeds 2 minutes consistently
- Security incident involving Netbird setup key
Steps:
1. Revoke Netbird setup key from GitHub Secrets
2. Remove Netbird join step from GHA workflows
3. Deploy self-hosted runner VM on Proxmox (V1 fallback)
4. Add runner registration token to GitHub Secrets
5. Update workflows to use self-hosted runner label
Blast radius: Pipeline only — no prod infra affected. Dev workstation read-only access unaffected.

**Refresh triggers:**
- Netbird deprecated or replaced in the stack
- GitHub Actions pricing or runner changes affect cloud runner availability
- Proxmox API moves behind stricter network controls
- Team grows beyond solo operator (re-evaluate secret management)

**Affected files:** .github/workflows/tofu-apply.yml, .github/workflows/tofu-plan.yml
